# Lens + Presence + OS-Intents — complete plan (rev 3: OBS-style texture plane, no WebSocket frames)

## Context

Measured this session (ADR 0009 + evidence): zero-activation navigation works, CG metadata = universal awareness, ScreenCaptureKit = background pixel observation (the pub.dev admin panel captured from a background window). AX is dead for background web on **all** browsers. Owner decisions locked: lens = **native Flutter view of any surface agents act on** (no webview); energy policy **configurable**; **presence pointers** for multiple agents (soft-only v1); OS-intents tier via **App Intents — Apple's cross-app invocation surface per 2026** (WWDC26 invoke/discovery APIs; intentcall was built with this intention — it declares/projects, UA executes); last_answer first host; pid-posted pointer experiment in scope.

**This revision replaces WebSocket frame streaming with the OBS capture model.** The objection was exact: the previous design serialized every frame (JPEG encode → Dart `Uint8List` → JSON/base64 → WebSocket → decode) — at 1440×900 × 5 fps that is 1.5–2.5 MB/s of Dart allocations plus base64 inflation and a copy at every hop: pure GC pressure for something the GPU already holds.

## How OBS does it (the model we follow)

1. **Capture delivers GPU textures, not bytes** — SCK on macOS (OBS 28+), Windows.Graphics.Capture on Windows, PipeWire on Linux; frames are CVPixelBuffer/IOSurface (macOS) or D3D11 textures (Windows), GPU-resident.
2. **The preview never serializes** — OBS composites and displays textures directly; nothing touches the CPU to "show" a source.
3. **Encode only at the output boundary** — VideoToolbox/NVENC runs when a recording/stream actually leaves the machine; our equivalent is the on-demand full-res grab for agent evidence.
4. **Per-source streams, damage-driven** — SCK delivers only-on-change for static content (a still admin page costs ~nothing).

Our two planes mirror this exactly:

- **Texture plane (the lens, human legibility)**: SCK window stream → IOSurface → `FlutterDesktopGpuSurfaceDescriptor` → texture registrar → `Texture` widget. **Zero Dart allocations per frame** ([Flutter macOS external textures](https://api.flutter.dev/macos-embedder/interface_flutter_external_texture.html), [Metal IOSurface textures](https://developer.apple.com/documentation/metal/mtldevice/maketexture(descriptor:iosurface:plane))).
- **Event plane (presence + receipts)**: tiny structured JSON events (agentId, windowId, pointer, receipt) — KB-scale, never frame bytes.
- **Byte plane (evidence / agent sampling)**: on-demand one-shots only — `windowScreenshot(windowId, maxPx)` (already proven: the admin PNG). The agent samples when it decides; no continuous byte path. `universal_screencast`'s byte pipeline stays for recorder/remote-later — explicitly out of the lens hot path.

## Phase 1 — `universal_automation_lens` as a Flutter PLUGIN (native texture capture in-host)

New `pkgs/universal_automation_lens/` — the workspace's first platform plugin (camera-plugin shape):
- **macOS native** (`darwin/`): `SCContentFilter(desktopIndependentWindow: window)` stream (the bridge today is display-wide only) → `CVPixelBuffer/IOSurface` → `FlutterTextureRegistrar` + `FlutterDesktopGpuSurfaceDescriptor` → textureId. Refcounted window-stream registry in-process (N lens widgets share one textureId); energy policy (`performance|balanced|saver` → fps ceiling/resolution; IOPS power state shifts defaults, never blocks — ADR 0061 pattern) applied via `SCStreamConfiguration` at stream create; screenRecording consent attaches to the **host app**.
- **Dart** (`lib/`): `LensView` (`Texture` + presence overlay + receipts), `LensController` (`attach(windowId)/detach`, `burst()`), presence model. First Flutter-deps package in the workspace (`resolution: workspace`; note Flutter environment).
- Windows/Linux engines (WGC→D3D texture, PipeWire→DMA-BUF) declared as follow-up phases — same plugin seam.
- The resident serve does NOT stream to the lens: capture lives in the host process; the serve remains the act/observe brain.

## Phase 2 — Presence + agentId (event plane)

- `automation_act`/`observe`/`computer` gain optional **`agentId`** (default: MCP clientInfo name) — parsed in `_attachSession`/`_session` (`pkgs/universal_automation_toolkit/lib/src/mcp/mcp_server.dart`), threaded into `SessionBinding.name` (`runner/registry.dart`) so consent receipts carry it free. `AutomationAction` stays pure.
- **PresenceBus** (new toolkit `lib/src/presence/presence_bus.dart`): agentId → {windowId, pointer, last receipt, ts}; v1 transport = a lightweight `automation_presence` MCP poll verb (JSON, KB-scale — never frames); WebSocket upgrade later only if cadence demands. **Soft collisions only** (overlap warnings in receipts).

## Phase 4 — OS-intents tier (executor for Apple's cross-app intent surface)

**Corrected analysis (2026)**: App Intents ARE the cross-app invocation mechanism — the system discovers/combines/invokes intents across apps ([WWDC26 session 345](https://developer.apple.com/videos/play/wwdc2026/345)); WWDC26 API set (`IntentValueRepresentation`, `RelevantEntities`, `EntityCollection`, `SyncableEntity`, `LongRunningIntent`, `IntentExecutionTargets` + invoke/discovery) is beta-shaped and Swift-first ([documented](https://www.theswift.dev/posts/build-app-intents-that-travel-across-apps-and-devices)); App Intents are replacing URL schemes ([analysis](https://medium.com/@bhumibhuva18/app-intents-are-quietly-killing-url-schemes-and-ios-26-is-finishing-the-job-8821f1599267)); apps must live in /Applications or intents fail silently ([forums](https://developer.apple.com/forums/topics/machine-learning-and-ai/machine-learning-and-ai-app-intents)).

New `pkgs/universal_driver_intents/` (macOS-first, behind `Platform.isMacOS`):
- **Primary**: small Swift bridge (the `capture_bridge` pattern) over the WWDC26 AppIntents invoke/discovery APIs; exact symbol binding against the installed 2026 SDK headers at implementation start (the bridge isolates beta churn).
- **Fallbacks**: `shortcuts list/run` CLI, `sdef` dictionary enumeration, URL entities/deep links.
- **Catalog seam**: implements `AutomationActionCatalog.actions()` (`universal_automation_interface/lib/src/automation_action_catalog.dart`) → perform via `InvokeAction`. Honest-by-absence.
- **Compose, don't migrate**: depend on published `intentcall_core` + `intentcall_schema` (1.3.x, pure Dart) for `AgentIntentDescriptor`/`InputSchema`/`AgentResult`; extend `pkgs/universal_automation_toolkit/test/intentcall_contract_test.dart` as the compatibility lock. intentcall keeps transport adapters + `platform_sync` (which already EMITS App Intents Swift into Flutter hosts — later last_answer declares lens actions as real App Intents through it). UA owns driving — the executor intentcall deliberately lacks.
